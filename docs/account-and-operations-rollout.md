# Account and Operations Rollout

This is a staging and operations checklist, not evidence that production services have been configured. Do not copy real credentials, encryption keys, recovery codes, or environment files into support messages or source control.

## Implemented in Draft 2

- Individual password login and logout with server-side sessions.
- Login and sensitive-account-action rate limiting. The default `memory://` store is per process and resets on restart. Set `RATE_LIMIT_STORAGE_URI` to an authenticated, TLS-protected Redis service shared by every worker before scaling. Never trust arbitrary client-provided forwarding headers as a client-IP identity. The global and account limits can themselves be used for denial of service; add edge protection and monitoring.
- Optional authenticator-app MFA with encrypted TOTP secrets, replay detection, ten one-use recovery codes, and password plus MFA confirmation before disabling it. Enabling or disabling MFA revokes other sessions. MFA is opt-in per user, not mandatory for all accounts.
- Password reset through SMTP STARTTLS, with generic responses, hashed one-use 30-minute links, and revocation of existing sessions. Resetting a password does not disable MFA. Without valid mail settings, the request fails clearly rather than pretending delivery occurred.
- Optional email verification with hashed one-use 24-hour links. `EMAIL_VERIFICATION_REQUIRED=false` by default. When enabled, new accounts must confirm email before sign-in. Existing accounts are grandfathered during migration, which is not evidence that their mailbox ownership was verified. Accounts created while enforcement was off may need to verify when enforcement is later enabled.
- Password-confirmed account deletion for accounts with no owned projects, and never for the last active administrator. MFA-enabled users must also supply a second factor. Account and session records are removed; this does not assert erasure from backups, operational logs, or historical orphaned media.
- A first-project onboarding prompt, browser-specific 404 page, form limits and field-specific validation errors, selected loading states, and mobile-viewport checks. Other pages and workflows may still need accessibility and usability work.
- Optional server-side Sentry error reporting. Nothing is sent unless `SENTRY_DSN` is configured. The event filter removes request data, user data, breadcrumbs, exception messages and stack-local variables; traces are disabled. The organization must approve the provider and assess its data handling before enabling it. This is not user analytics.

## Required staging setup

1. Make and independently verify a database backup and a Spaces/media backup. Test restore to a separate, isolated environment before modifying production. A database-only backup does not include Spaces objects, and a point-in-time database restore can point to media that has since changed or disappeared.
2. Provide `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, and, if required, `SMTP_USERNAME` and `SMTP_PASSWORD` through the protected server environment. The implementation uses STARTTLS with certificate validation. `PUBLIC_APP_ORIGIN` defaults to `https://APP_DOMAIN`; in production an explicit origin must be an allowed HTTPS origin. Test real delivery, sender authentication, spam filtering, expired links, and single-use behavior before relying on recovery.
3. Generate an independent Fernet key for `MFA_ENCRYPTION_KEY` using a secure administrator-controlled environment. Store and back up that key separately from the database, restrict access, and do not paste it into chat or logs. Preserve the same key across restarts and replicas. Losing or rotating the key without migration prevents TOTP secrets from being decrypted; unused recovery codes can still authenticate and disable MFA if the password is known. Users must save their one-time recovery codes securely. No administrator MFA-recovery interface is included.
4. Configure a shared Redis `RATE_LIMIT_STORAGE_URI` before using more than one app worker or replica. Restrict its network access, require authentication and TLS, and verify that loss of Redis prevents startup. The rate limiter is not a DDoS defense and is not a replacement for edge throttling.
5. If approved, configure `SENTRY_DSN` privately and send a controlled test error. Verify the received event contains no credentials, URLs, tokens, user details, exception messages, or local variables. Do not enable a third-party provider until its privacy and data-residency implications are approved.
6. Only after email delivery and legacy-account impact are checked, consider setting `EMAIL_VERIFICATION_REQUIRED=true`. Startup fails if required mail/public-origin settings are missing. Confirm an existing administrator can still sign in and a new test account can verify before broader rollout.
7. Validate the Compose file and Caddy configuration in staging with Docker installed, then exercise login, logout, reset, verification, MFA enrollment/recovery, account deletion, project creation, uploads, media viewing and share links. These integrations have local automated tests, but real PostgreSQL locking, SMTP delivery, Redis connectivity, and the production proxy have not been independently validated here.

## Backup and recovery ownership

The repository does not enable or schedule production database backups. An administrator must inspect the managed PostgreSQL provider's actual backup/retention settings, assign an owner, define recovery-point and recovery-time objectives, and monitor failures. Arrange independently protected backups or versioning for Spaces objects. `app.restore_verify` can compare restored database table counts and hashes of referenced objects against a protected inventory manifest; it does not create backups or prove scheduling, retention or recovery objectives. See [data-protection-rollout.md](data-protection-rollout.md) for a controlled restore procedure. PostgreSQL logical dumps can be useful supplements but do not by themselves back up cloud objects or all cluster-wide roles; version compatibility and restore privileges must be checked.

For a DigitalOcean managed PostgreSQL cluster, DigitalOcean documents automatic daily backups with seven-day retention. Verify the actual cluster and plan rather than assuming this service is enabled for every database. A restore creates a new cluster and can incur charges: open the database's Overview page, choose **Actions > Restore from backup**, select a recovery point, and restore to a new, isolated cluster. Never destroy the original cluster during a drill; DigitalOcean warns that destroying a cluster also destroys its provider-held backups. Reference: https://docs.digitalocean.com/products/databases/postgresql/how-to/restore-from-backups/

## Remaining work and decisions

- **Isolated media processing:** Draft 2 now routes PDF, preview and telemetry work through a constrained, networkless worker container. Visual odometry is disabled in this mode. Docker Compose and representative camera-file behavior still require staging validation before calling the production deployment sandboxed.
- **PostgreSQL row-level security:** Project, pin, annotation and share-link policies and request-scoped transaction identity are implemented and tested against disposable PostgreSQL. RLS is not active on an existing deployment until a separate non-owner runtime role is provisioned, the policies are applied, grants are checked and `DATABASE_REQUIRE_RLS=true` is enabled. Account/session tables are not covered. Follow [data-protection-rollout.md](data-protection-rollout.md); do not apply directly to production without a restore and staging drill.
- **Analytics:** Optional first-party daily aggregate counts are available with explicit browser consent and are disabled by default. Review and publish the actual privacy notice before enabling `ANALYTICS_ENABLED=true`; server access logs are separate and user consent does not erase prior aggregate counts.
- **Privacy policy and terms:** These legal pages are not yet published. The organization must supply its legal entity and contact details, actual retention/deletion practices, providers and locations, applicable jurisdiction, user rights and reviewed terms before publishing. Do not substitute invented legal claims.
- **API keys:** No application API keys were found in the reviewed frontend files. This is not a secret-history or infrastructure audit; run a dedicated secret scanner and rotate any credentials discovered to have been exposed.
- **Production safeguards:** Complete cloud IAM, private bucket, network/firewall, database certificate verification, server patching, backups, audit logging, alerts, incident response, and an independent penetration test. The live server and cloud configuration were not inspected by this work.
