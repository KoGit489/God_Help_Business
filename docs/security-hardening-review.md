# Draft 2 Security Hardening Review

This document records the scope and limits of the security review. It is not a penetration test, certification, or proof that the application is free of vulnerabilities.

## Hardened in this change

- **SQL injection:** Project and account operations use SQLAlchemy ORM expressions and bound parameters. Schema migration SQL uses application-owned static identifiers, not request data. A database-backed regression verifies a SQL-injection-shaped project title is stored as data. This does not substitute for database privilege review or an independent penetration test.
- **Stored HTML injection:** Project details, pin information, notes, error messages, filenames, and public shared-review text are escaped or rendered as text rather than interpreted as markup. Regression tests and an isolated browser test exercise hostile markup. The remaining `innerHTML` uses must be reviewed when changing the frontend.
- **Credential redirection:** An `apiBase` override must resolve to the page's own HTTP(S) origin. Sign-in return URLs must remain on the same origin. External API overrides used for development no longer work; serve the frontend and API on the same origin or explicitly configure a reverse proxy.
- **Indirect object access:** Native capture processing only accepts media keys belonging to the current project and waypoint, including the supported legacy direct-upload location. Cross-project and traversal keys are rejected before object storage is read. Existing legacy records pointing outside those locations may need to be reuploaded.
- **Early upload authorization:** In authenticated mode, upload routes check the session and project owner before multipart parsing, reducing exposure to unauthenticated or cross-owner upload bodies.
- **Unsafe media types:** Media responses use server-selected safe types rather than trusting object metadata. Native and unknown types are sent as downloads, and responses set `X-Content-Type-Options: nosniff`.
- **Request size:** Uploads without `Content-Length` and streamed writes with `Transfer-Encoding` are rejected. Declared upload sizes are checked before multipart parsing, and non-upload requests with declared lengths are limited to 1 MiB. Clients that use streaming/chunked uploads must send a known length instead. Proxy and application-server limits should additionally be configured and tested for all HTTP versions; this is not a complete streaming resource-control system.
- **Production configuration:** Production startup requires authentication, secure cookies, and one or more exact HTTPS CORS origins. Production Compose sets `APP_ENV=production` and must be started with the real `APP_DOMAIN` in the protected environment file.
- **Proxy headers:** Caddy uses `Referrer-Policy: no-referrer`, same-origin framing, and a partial Content Security Policy for `frame-ancestors`, `base-uri`, and `object-src`. Same-origin frames remain allowed for the floor-plan PDF fallback. This is not a full script-restricting CSP.
- **Login and password confirmation:** A moving-window limiter allows 10 sign-in/password-confirmation attempts per account per minute and 120 globally per minute. Unknown accounts perform a dummy Argon2 verification. The default limiter is process-local; `RATE_LIMIT_STORAGE_URI` can point to a shared Redis service. Startup fails when its configured store is unavailable. These limits can be used to deny service to an account and are not a substitute for trusted client-IP and edge abuse controls.
- **Account deletion:** Authenticated users can request account deletion after confirming their password. Deletion revokes all sessions and is blocked for project owners and the last active administrator. It removes the account and session records; it does not promise deletion from backups, operational logs, or historical orphaned media.
- **Error monitoring:** A server-side Sentry SDK integration is disabled unless `SENTRY_DSN` is configured. Its event filter removes request data, user data, breadcrumbs, exception messages and stack-local variables; traces are disabled. The organization must approve the provider and review the resulting data flow before enabling it. This does not install user analytics.
- **Password recovery and email verification:** Optional SMTP STARTTLS delivery uses hashed, single-use reset and verification tokens that expire after 30 minutes and 24 hours respectively. Token links use URL fragments, and resetting a password revokes sessions without disabling MFA. Requests return the same generic response for known and unknown accounts. Configure and test SMTP before enabling verification; it is off by default. Existing accounts are grandfathered as verified during migration, which is not proof of mailbox ownership.
- **Authenticator MFA:** Users may enable TOTP after confirming their password. Secrets use Fernet encryption under the server's `MFA_ENCRYPTION_KEY`; recovery codes are shown once and stored as hashes. Used TOTP counters and recovery codes cannot be reused. Enabling or disabling MFA revokes other sessions, and MFA-enabled account deletion requires a second factor. A lost encryption key prevents authenticator-code validation; unused recovery codes can still be used. Keep the key stable and back it up separately. MFA is opt-in and requires staging validation and a documented support/recovery process before rollout.
- **User experience:** First-project onboarding, browser 404 pages, loading states for account/project submissions and field-specific validation messages are available. API validation errors no longer echo submitted input such as passwords.
- **Build and static exposure:** Docker's build context is restricted to the application, frontend, Dockerfile and dependencies, with environment files, private-key formats and Git metadata excluded. The public static-file mount rejects hidden files and directories. Caddy receives only `APP_DOMAIN` instead of the full application environment. Review the build context and server filesystem in staging; arbitrary secrets accidentally placed in other public frontend files can still be exposed.
- **Logs and caches:** The production image disables Uvicorn access logs to avoid logging bearer share URLs, SQLAlchemy hides bound query parameters, request IDs are restricted to safe characters and sensitive API/media responses use `private, no-store`. This does not control logs from the cloud load balancer, reverse proxy, database, SMTP, container runtime, monitoring service or browser history. Review their configuration and retention separately.
- **Production exposure:** Interactive API documentation is unavailable in production. Object-storage endpoints must use HTTPS and cannot embed credentials, query strings or fragments. This does not prove that the bucket is private or that cloud access policies are least-privilege.
- **Authorization and input:** Authentication now binds the user identity to PostgreSQL transaction-local RLS context before account actions, and authenticated review access has no demo-user bypass. Waypoint coordinates, finite headings and database-backed string lengths are validated server-side. Tests exercise cross-owner project, media, annotation and sharing access and account deletion against a real restricted PostgreSQL role.
- **RLS readiness:** Strict RLS mode rejects a runtime role that can assume project-table ownership, truncate protected tables, join privileged roles, create in the policy schema, or encounter additional project-table policies. The check verifies policy names and commands, not the exact policy expressions or the source of every indirect privilege. RLS uses application-supplied PostgreSQL settings: a compromised runtime credential or arbitrary SQL execution can change those settings, so RLS is defense in depth, not a boundary against a hostile database user.
- **Supply chain:** A read-only CI workflow runs backend/frontend tests, dependency checks and redacted Gitleaks source/history scans. GitHub Actions revisions and the scanner archive checksum are pinned. The workflow was validated locally but has not yet run on GitHub; its normal tests do not start a PostgreSQL service, and base container images, OS packages and Python transitive dependencies are not locked by hash.

## AI and Workflow Risks

No autonomous AI agent, prompt-processing endpoint, Firebase, Supabase or NoSQL database is implemented in the reviewed application. If AI tools are introduced, treat uploaded captures, project text, browser pages, GitHub issues, comments and tool output as untrusted data rather than instructions. Do not send secrets or private project data to an external model without approval; scope tool credentials to the minimum needed, require human approval for deployment and destructive actions, and record provider, retention and residency decisions. CI uses `pull_request`, not `pull_request_target`, has read-only repository permissions, and does not persist checkout credentials; never add production secrets to untrusted pull-request jobs.

## Security Review Limits

A local Gitleaks 8.28.0 scan of reachable Git history and the application, frontend, deployment, documentation and test directories found no matches. Scanners have false negatives; this does not cover deleted/unreachable history, external repositories, server files, container registries, build logs, cloud configuration, or all possible secret types. If a real secret is found, revoke and rotate it first, review access logs, and coordinate history cleanup; deleting a commit does not invalidate a credential. Do not paste credentials, environment-file contents or unredacted scanner reports into chat.

The operator must independently verify that Spaces is private, public ACLs and public policies are disabled, credentials have only the required bucket operations, database and Redis access are network-restricted, and the database runtime login is non-owner/non-superuser/non-`BYPASSRLS`. Prefer PostgreSQL `sslmode=verify-full` with the managed provider's CA certificate; `sslmode=require` encrypts traffic but does not verify the server's identity. Rotate any suspected exposed keys and database passwords, preserve recovery keys separately, and enforce least privilege on CI and production secret stores. These settings cannot be verified from this checkout.

## Remaining priorities

1. Configure shared rate-limit storage before scaling, add edge and upload rate limits with a trusted client-IP strategy, and monitor account abuse. The default in-memory limiter is not sufficient for multiple workers or replicas; trusting arbitrary forwarding headers is unsafe.
2. Configure and test SMTP, MFA key storage and backup, account-recovery support, session inventory, and a real project-sharing authorization model. The implementation is not a substitute for an established identity provider or an independent authentication review.
3. Enforce request-body and decoded-image limits on streaming input at the proxy and application layer. Isolate native-media and PDF parsing in a resource-limited worker, scan uploaded content, and configure container CPU/memory/disk limits. Signature checks alone do not prove a file is safe.
4. Minimize share-token leakage through access logs and retention, consider storing share-token hashes, and define an explicit authorization model for any media shared with guests.
5. Replace remaining dynamic HTML construction with safe DOM APIs where feasible; add a restrictive CSP after removing incompatible inline scripts and auditing external browser libraries. Pin and verify frontend assets, container images, and system packages independently of Python dependencies.
6. Verify cloud firewall rules, SSH policy, managed database TLS certificate verification, Spaces bucket privacy and IAM, server patching, backups, restore drills, monitoring, audit logging, secret rotation, and incident-response ownership. Repository visibility and the live server configuration were not verified in this local review.
7. Test with representative `.insp`/`.insv` captures, PostgreSQL, DigitalOcean Spaces and the production proxy in a staging environment; conduct an independent security assessment before treating the service as production-hardened.

## Operational cautions

- The database migration and security configuration should be tested against a staging copy and a current database backup before deployment.
- Health endpoints do not establish that Spaces is accessible or that uploads, authorization, or review links work end to end.
- Local unit tests and a Python dependency audit do not validate production image/OS packages or future vulnerabilities.
- Do not commit credentials or post secrets in logs or support messages.
